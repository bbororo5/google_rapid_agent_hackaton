# L0. 제품 정의서

| 항목 | 내용 |
|---|---|
| 버전 | v1.2 (초안) |
| 작성일 | 2026-07-15 |
| **제품 단계** | **프로토타입(PoC - 개념 검증, 아이디어가 실제로 동작하는지 확인하는 단계).** 서비스 운영 단계가 아니다. 이 문서의 성공 기준은 §6의 검증 가설이며, 운영 지표는 §6.3으로 이월해 둔다 |
| 답하는 질문 | 왜 만들고, 누구의 어떤 문제를 푸는가, 이 단계에서 무엇이 증명되면 성공인가 |
| 답하지 않는 질문 | 어떤 화면인가(L2), 어떻게 동작하는가(L4) - 이 문서에 해법의 형태는 등장하지 않는다 |

## 1. 문제

소셜 미디어를 직접 운영하는 마케터는 지표를 매일 본다. 그러나 세 가지 질문에 답하지 못한다.

1. **원인** - 이 수치는 왜 이렇게 나왔는가?
2. **처방** - 다음에 무엇을, 언제까지, 어느 수준으로 해야 하는가?
3. **회고** - 지난번에 하기로 한 것은 실제로 어떻게 되었는가?

이 세 질문은 연결되어 있다. 원인을 모르면 처방이 감에 의존하고, 회고가 없으면 같은 실수가 반복된다. 문제의 본질은 정보 부족이 아니라 **해석과 실행 사이의 단절**이며, 이 단절은 반복되는 루프(원인 → 처방 → 실행 → 회고)가 아무 도구의 지원도 받지 못하기 때문에 발생한다.

기존 대안이 이 문제를 풀지 못하는 이유:

| 대안 | 한계 |
|---|---|
| 지표 대시보드 (Metricool 등) | 숫자를 보여줄 뿐, 세 질문 중 어느 것에도 답하지 않는다 |
| 범용 AI 챗봇 | 그럴듯한 조언을 하지만 근거가 없고, 지난 대화를 책임지지 않는다 |
| 마케팅 대행사 | 세 질문에 답하지만, 우리 타깃은 비용을 감당할 수 없다 |

## 2. 대상 사용자

**1차: 한국의 소규모 연예 기획사(아이돌 매니지먼트)와 1~5인 브랜드의 소셜 마케팅 담당자.**
대표 사용자상은 소속 아이돌·아티스트의 SNS 채널을 직접 운영하는 소규모 기획사의 담당자다. Instagram·X·YouTube·TikTok을 직접 운영하고, 대행사를 쓸 예산이 없다. 지표 확인은 습관이지만 회고는 습관이 아니다 - 계획을 세워놓고 잊어버리는 것이 보통이다. 초기 카테고리는 연예(아이돌), 뷰티, 푸드 3개이며 한국 시장을 우선한다.

성실하게 스스로 회고하는 소수는 우리 없이도 잘한다. **우리가 도울 사람은 잊어버리는 다수다.** 이 정의가 제품의 여러 결정(시스템이 기억을 대신 지는 것)의 근거가 된다.

## 3. 제품 정의와 가치 제안

**LaunchPilot은 소셜 마케팅의 원인-처방-회고 루프를 대화로 진행하게 해주는 AI 컨설턴트다.**

가치 제안은 세 가지 약속이다.

1. **모든 답에는 근거가 있다.** 조언은 두 가지 지식에서만 나온다: (a) 소셜 트렌드에 대한 구조화된 관찰 - 지금 무엇이 왜 통하는지, 그리고 그 유행이 어느 단계에 있는지. (b) 현직 마케터의 노하우 - 지표를 어떻게 읽고 다음 행동을 어떻게 정하는지. 이 두 지식이 답변 안에서 출처로 드러난다.
2. **합의한 계획은 사라지지 않는다.** 대화에서 정한 다음 행동은 기록으로 남고, 예정된 확인 시점이 되면 시스템이 결과를 준비해둔다. 사용자가 잊어도 루프는 닫힌다.
3. **모르는 것은 모른다고 한다.** 근거가 부족하면 조언을 지어내는 대신 부족하다고 말한다. 데이터가 오래됐으면 오래됐다고 말한다. 컨설턴트의 신뢰는 맞출 때가 아니라 한계를 인정할 때 쌓인다.

## 4. 제품 전략 원칙

**판단은 범용 AI에 맡기고, 우리는 자산을 축적한다.**
특정 작업에 특화된 AI 컴포넌트는 범용 모델의 발전 속도를 따라가지 못해 유지보수 부채가 된다. 우리의 경쟁력은 AI 자체가 아니라 AI에게 먹일 재료다: 트렌드 관찰의 축적, 마케터 노하우의 축적, 사용자별 맥락의 축적, 그리고 좋은 답과 나쁜 답을 가르는 기준의 축적. 모델이 좋아질수록 같은 자산에서 더 좋은 답이 나오는 구조를 유지한다.

**전 세계 실시간 트렌드 경쟁은 하지 않는다.**
플랫폼 추천 알고리즘과의 속도 경쟁은 구조적으로 불가능하다. 대신 사용자의 카테고리로 범위를 좁히고, 유행의 성격(빠르게 소멸하는 것 / 재현 가능한 것 / 변하지 않는 것)에 따라 다르게 다루며, 데이터의 시점을 정직하게 밝힌다.

## 5. 범위

**프로토타입에 포함:** 캠페인 진단·계획·회고 루프 1회전. 구조는 3개 카테고리 × 4개 채널을 수용하되, 검증용 데이터는 집중 카테고리 1개만 구축한다(§6.1). 지표 데이터는 가상 데이터, 두 지식 원천(트렌드 관찰·마케터 노하우)은 수동 구축한 표본으로 시작한다. 실데이터 파이프라인(실제 소셜 지표를 자동 수집해 오는 경로)은 교체 가능한 부품으로 설계만 유지한다. 검증 대상 시나리오는 L1에서 정의한다.

**프로토타입에서 제외:**
- 콘텐츠 자동 게시·계정 자동 운영
- 광고 집행·예산 최적화
- 범용 지표 대시보드 (기존 도구의 영역)
- 실시간 전 세계 트렌드 피드 (원칙 §4)
- 실제 소셜 API 연동, 다국어·해외 시장
- 회원 체계·과금 등 운영 인프라

## 6. 이 단계에서 검증하려는 가설 (PoC 성공 기준)

프로토타입의 성공은 사용자 수나 유지율이 아니라, **아래 가설들이 증명 또는 반증되는 것**이다. 반증도 성공이다 - 늦게 아는 것만이 실패다.

### 6.1 검증 가설

검증은 두 단계로 진행한다. **1차는 개발팀의 직접 사용**(도그푸딩 - 만든 팀이 자기 제품을 실제 사용자처럼 직접 써보는 검증 방식)으로 동작의 사실 여부와 형식 요건을 판정하고, **2차는 현직 마케터 평가로 이월**해 실무 유용성을 판정한다. 개발팀은 유용성을 판정할 자격이 없으므로 1차에서 유용성 통과를 선언하지 않으며, 마케터에게 동작 검증을 시키는 것은 낭비이므로 2차는 유용성에만 집중한다.

**1차 - 개발팀 (지금):**

| # | 가설 | 판정 방법 | 통과 기준 |
|---|---|---|---|
| H1a | 답변이 형식 요건을 갖춘다 - 근거·출처·시점이 붙고, 다음 행동이 기간·지표·예상 범위와 함께 나온다 | 대표 시나리오의 답변을 체크리스트로 검사 | 전 답변이 형식 요건 충족 |
| H2 | 원인-처방-회고 루프가 끝까지 동작한다 | 가상 데이터로 진단 → 계획 합의 → 시점 도래 → 결과 확인의 전체 루프를 중단 없이 완주 | 대표 시나리오 전 구간 완주. 중간에 사람의 데이터 수선 개입 없음 |
| H3 | 시스템이 근거를 지어내지 않는다 | 검증 세션 전체에서 답변의 출처를 원본 데이터와 대조 | **화면에 도달한 답변 기준** 근거 날조 0건 (생성 단계의 환각을 0으로 만드는 것이 아니라, 위반 출력이 사용자에게 닿지 않음을 검증). 근거 부족 상황에서 "모른다" 응답이 실제로 나옴 |
| H4 | 대화형 분석의 대기 시간이 수용 가능한 수준이다 | 무거운 분석의 응답 시간을 반복 실행으로 측정 + 팀 직접 사용 소감 | 반복 실행의 90% 이상이 수십 초 이내 (외부 모델 API의 지연 변동은 통제 밖이므로 "항상"은 정의하지 않음) |

**왜 이 네 가지인가.** PoC는 모든 것을 검증하는 단계가 아니라, 틀렸을 때 대가가 가장 큰 가정부터 검증하는 단계다(린 스타트업의 "가장 위험한 가정 우선" 원칙). 네 가설은 각각 알려진 실패 유형에 대응한다.

- **H1a·H3 (근거·날조):** LLM은 그럴듯한 거짓을 자신 있게 말하는 환각이 대표적 실패 모드다. 근거 데이터를 주고 그 안에서만 답하게 하는 접근이 이를 줄인다고 알려져 있지만, 우리 데이터와 우리 도메인에서 실제로 되는지는 검증 전까지 가정이다. 이게 깨지면 "근거 있는 컨설턴트"라는 제품 자체가 성립하지 않는다 - 가장 위험한 가정.
- **H2 (루프 완주):** 기존 대안들이 못 하는 것이자 우리의 핵심 차별점이 "회고까지 이어지는 루프"다. 차별점이 기술적으로 성립하는지가 두 번째로 위험한 가정.
- **H4 (대기 시간):** 대화형 분석은 지표 조회, 트렌드 대조 등 여러 단계를 거쳐 수십 초가 걸리는 구조다. 사용성 연구에서 10초를 넘는 대기는 사용자의 주의가 이탈하는 구간으로 알려져 있어, 대화형이라는 형태 선택 자체가 리스크를 안고 있다. 반증되면 프롬프트 수정이 아니라 제품 형태(대화형 vs 사전 계산 리포트형)의 재검토가 필요하다.

**2차 - 현직 마케터 (이월):**

| # | 가설 | 판정 방법 | 통과 기준 |
|---|---|---|---|
| H1b | 근거가 붙은 조언을 현직 마케터가 "실무에 쓸 만하다"고 평가한다 | 마케터 3~5명이 직접 사용 후 답변별 평가 + 인터뷰 | 답변 과반이 "쓸 만함" 이상, "못 쓴다" 사유가 수집·분류됨 |

집중 카테고리는 1개로 좁힌다 - 3개 분량의 가상 데이터·지식 준비는 검증력 증가 없이 비용만 3배다. 1차 집중 카테고리는 **연예(아이돌)**로 한다. 팀의 기준 도메인이 연예 기획사(아이돌 매니지먼트)여서 요구사항과 가상 데이터의 현실감을 자체 판단할 수 있는 카테고리이고, §2의 대표 사용자상과도 일치한다. 2차에서 확보된 마케터의 카테고리가 다르면 데이터 표본만 교체한다(구조는 재사용).

### 6.2 명시적 비목표 (이 단계에서 재지 않는 것)

리텐션(사용자가 계속 돌아오는 비율), 전환율(방문자가 목표 행동까지 가는 비율), 규모 확장성, 비용 효율. 실사용자와 운영 기간이 없는 단계에서 이 숫자들은 측정 불가능하며, 흉내 내면 허수가 된다.

### 6.3 운영 단계로 이월하는 지표 (정의만 보존)

PoC 통과 후 서비스 단계에서 측정을 시작할 지표의 정의만 남겨둔다: 루프 완결률(합의된 계획 중 결과 확인까지 간 비율), 재방문 유지율, 조언 수용률, 근거 관련 불만 빈도(역지표 - 낮을수록 좋은 지표).

## 7. 가정

이 문서가 참이라고 전제하는 것들. 깨지면 상위 결정부터 재검토한다.

1. 가상 데이터로도 1차 검증(H1a~H4)에 충분한 현실감을 만들 수 있다.
2. 마케터 노하우는 1차에서는 공개 자료·팀 리서치로 구성한 표본으로 시작할 수 있다 (현직 노하우 수집은 2차와 병행).
3. 범용 LLM의 판단 품질이 "근거를 주면 쓸 만한 조언" 수준에 이미 도달해 있다.

## 8. 리스크

| 내용 | 대응 |
|---|---|
| 가상 데이터가 현실감이 없어 평가 자체가 무의미해질 수 있다 | 데이터 설계 시 실제 지표 분포 참조 |
| 트렌드 관찰의 신선도 한계가 조언 신뢰를 깎을 수 있다 | 시점 정직 표시 원칙 (L1 인수 기준으로) |
| 개발팀 자체 평가(1차)는 확증 편향(자기가 만든 것이라 잘 된 결과만 눈에 들어오는 치우침)에 취약하다 | H1a는 주관 평가 대신 형식 체크리스트로만 판정. 유용성 판단은 1차에서 선언하지 않음 |

## 9. 용어 (이후 모든 층이 상속)

| 용어 | 정의 |
|---|---|
| 캠페인 | 사용자가 정의한 마케팅 활동 단위. 목표와 기간을 가진다 |
| 채널 | Instagram, X, YouTube, TikTok |
| 카테고리 | 콘텐츠 도메인: 연예(아이돌), 뷰티, 푸드 |
| 연예 기획사 | 아이돌·아티스트를 매니지먼트하며 그 SNS 채널을 운영하는 회사. 본 문서의 대표 사용자상 |
| 루프 | 원인 진단 → 다음 행동 합의 → 실행 → 결과 확인 → 개선의 반복 |
| 두 지식 원천 | 소셜 트렌드 관찰 + 현직 마케터 노하우 |
